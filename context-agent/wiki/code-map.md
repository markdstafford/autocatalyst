Orchestrator service ingress routes (added by Story 7-9):

- `POST /v1/conversations` — create a conversation, topic, optional message, run, and initial run step atomically; returns the created `Conversation`/`Topic`/`Message?`/`Run`/`RunStep`. Body schema: `createConversationWithFirstRunRequestSchema` from `@autocatalyst/api-contract`.
- `GET /v1/runs` — one filterable, cursor-paged page of the authenticated tenant's runs (filter-page-run-list enhancement, issue #133). Strict query schema `listRunsQuerySchema` (`packages/api-contract/src/run.ts`): `status`, `waitingOn`, `workKind`, `projectId` each take **one comma-separated value** (items OR within a field, fields AND across; repeated keys/arrays, empty items, unknown fields, invalid enum values, and bad limits all return `400 validation_error`); `limit` defaults to and is capped at `maxRunListLimit` (100); `cursor` is an opaque base64url string. The route decodes the cursor via `decodeRunListCursor` (malformed → `400`), passes normalized options into `ControlPlaneService.listRuns`, and encodes the repository's structured `nextCursor` via `encodeRunListCursor`. Response is `runListResponseSchema` = `{ runs: Run[]; nextCursor?: string }`; `nextCursor` is present only when more matching rows exist. Database-level filtering, newest-first ordering (`createdAt DESC, id DESC`), cursor predicate, project join, and `limit + 1` pagination live in `DrizzleRunRepository.listByTenant` (`packages/persistence/src/domain-repositories.ts`), which returns `{ runs, nextCursor? }` and resolves each row's `projectId` through a single run→topic→conversation join (constant-query, never N+1). `status`/`waitingOn` filters are translated into stored-column predicates derived from the run-step catalog.
- `GET /v1/runs/:id` — return the run for the authenticated tenant. 404 if missing; 403 if cross-tenant. Run responses from list/get/reply/recover include the API read-only fields `waitingOn` (derived from the run-step catalog), `status` (derived from `terminal`+`currentStep`: non-terminal → `in_progress`, else `done`/`failed`/`canceled`), and `projectId` (resolved via topic→conversation). These three are API-read-only — persisted rows and **run events do not carry `status`/`projectId`** (events keep the persisted+`waitingOn` shape); clients treat state-transition events as invalidation triggers and re-read the run. The single source for these fields is `mapRunToApiRun` in `packages/core/src/control-plane-service.ts`; single-run project resolution uses the optional `RunRepository.resolveProjectId`.
- `GET /v1/runs/:id/steps` — list run-steps for a run ordered by `(startedAt, id)`. 404/403 like above.
- `GET /v1/runs/:id/events` — Server-Sent Events stream of `ClientRunEvent` frames for the given run+tenant. Streams full runner event vocabulary (assistant turns, tool activity, progress, notifications, step checkpoints, terminal results) plus state transitions. Route subscribes before replaying so no events are lost during reconnect; replayed events are written first, then live events from the subscription. Each frame has `event: <type>`, `id: <eventId>`, and `data: <json>` lines. `Last-Event-ID` header triggers replay-after-cursor; unknown or expired cursors return HTTP `409 Conflict` with JSON `{ error: { code: "run_event_replay_cursor_unknown" | "run_event_replay_cursor_expired", message, lastEventId } }` before any SSE bytes (no `: connected` comment). **Retained SSE replay (opt-in):** `?replay=retained` query parameter replays only the durable retained-event history when explicitly set; without this parameter, plain streams (with or without `Last-Event-ID`) are live-only — cursor-based reconnect is the only way to replay without `replay=retained`. Implementation: `routes.ts` parses `replay: z.enum(['retained']).optional()`, `control-plane-service.ts` `SubscribeRunEventsInput` accepts `replay?: 'retained'`, and `run-events.ts` `InMemoryRetainedRunEventStore.replayAfter` replays all retained events when `replay === 'retained'` and no cursor is given.

Spec review routes (added by spec-review API surface enhancement):

- `GET /v1/runs/:id/spec` — returns the run's spec artifact with rendered markdown and parsed frontmatter. Policy resource: `run_spec`/`run_spec.read`. 404 if spec not found; 403 if cross-tenant. Response schema: `runSpecResponseSchema` (`{ artifact, markdown, frontmatter }`).
- `POST /v1/runs/:id/feedback` — creates artifact feedback for the run. Body schema: `createRunFeedbackRequestSchema` (`{ target: 'artifact', title, body, anchor? }`). Always creates with `status: 'open'`. Policy resource: `run_feedback`/`run_feedback.create`. Returns 201 with `Feedback`. Status lifecycle transitions (address/resolve/wont_fix/reopen) are NOT exposed here — no PATCH routes exist. **Anchor contracts:** `anchor` uses `artifact_range` kind with `from`/`to` fields that are zero-based Unicode codepoint offsets into the rendered Markdown string (use `[...str]` to count in JavaScript); `to` must be strictly greater than `from`. This is defined in `packages/api-contract/src/domain-value-objects.ts` `feedbackAnchorSchema`.
- `GET /v1/runs/:id/feedback` — lists all feedback for the run scoped to the caller's tenant. Policy resource: `run_feedback`/`run_feedback.list`. Returns 200 with `{ feedback: Feedback[] }`.
- `POST /v1/runs/:id/feedback/:feedbackId/thread` — appends a reply to an existing feedback item's thread without changing the feedback status. Policy resource: `run_feedback.thread.append`. Returns 200 with the updated `Feedback`. Body schema: `appendFeedbackThreadRequestSchema` (`{ body }`). Implemented in `packages/core/src/feedback-lifecycle.ts` (`appendFeedbackThreadReply`) and `packages/persistence/src/domain-repositories.ts` (`DrizzleFeedbackRepository.appendFeedbackThread`); exposed via `packages/sdk/src/client.ts` (`appendFeedbackThread(runId, feedbackId, request)`).

Run recovery route (added by recover-failed-run feature, issue #121):

- `POST /v1/runs/:id/recover` — reopens a `failed` terminal run and admits it for dispatch. Route module/path: `packages/api-contract/src/run-recovery.ts` (`runRecoveryPath = '/v1/runs/:id/recover'`, `runRecoveryModeSchema` = `resume|start_over`, strict `runRecoveryRequestSchema` `{ mode? }`, `runRecoveryResponseSchema` `{ run, mode }`, `recoverRunSuccessStatusCode`); registered in `packages/core/src/routes.ts` (missing body parsed as `{}`). Policy: `run_recovery.create` / `{ kind: 'run_recovery' }` in `packages/core/src/policy.ts`. Service method: `ControlPlaneService.recoverRun` in `packages/core/src/control-plane-service.ts` — authorizes, rejects model principals (403), resolves the stopped step and recovery plan via `packages/core/src/run-recovery.ts` (`findStoppedStep`, `resolveRecoveryPlan`, `RunRecoveryDependencies`, `RunRecoveryWorkspaceError`), materializes the workspace before reopening, reopens atomically, emits a `run_recovery` run event (`createRunRecoveryEvent` in `packages/core/src/run-events.ts`), and admits dispatch via `Orchestrator.admitForDispatch`. Repository transaction method: `RunRepository.recoverFailedRun` (interface in `packages/core/src/domain-repositories.ts`; `DrizzleRunRepository.recoverFailedRun` in `packages/persistence/src/domain-repositories.ts`) — atomic reopen that clears terminal/failureReason, creates a new open `RunStep`, preserves prior rows, and maps the one-active-run constraint to `ActiveRunConflictPersistenceError`. Workspace provisioning replacement option: `existingWorkspaceBehavior: 'keep' | 'replace'` on `ProvisionWorkspaceRequest` (`packages/execution/src/workspace.ts`), honored by `packages/execution/src/internal/workspace-provisioner.ts` — `replace` rebuilds the run's own derived branch/root from the freshly fetched default branch even when the workspace is present on the expected branch; all existing callers default to `keep`. Server wiring: `recoveryDependencies` in `apps/control-plane/src/server.ts` implements commit detection (run-branch head vs `provisionedBaseRef` via the run workspace git port) and materialization (via `provisionWorkspace`). SDK: `ControlPlaneClient.recoverRun(id, request?)` in `packages/sdk/src/client.ts`. Reply behavior: `ControlPlaneService.replyToRun` returns a 409 naming `POST /v1/runs/:id/recover` for a `failed` run and a 409 stating cancellation cannot be recovered for a `canceled` run.

## Package generation path

Use the built-in Nx JavaScript library generator. This concrete example creates an adapter-scoped package named `example-provider`; use the same command shape for each future package and change only the two shell variable values before running it:

```bash
PACKAGE_NAME=example-provider
PACKAGE_SCOPE=adapter
pnpm nx g @nx/js:library "packages/${PACKAGE_NAME}" \
  --bundler=tsc \
  --unitTestRunner=vitest \
  --linter=eslint \
  --importPath="@autocatalyst/${PACKAGE_NAME}" \
  --strict=true \
  --minimal=true
```

After generation, verify or add these concrete fields for the `example-provider` package in `packages/example-provider/project.json`:

```json
  "projectType": "library",
  "tags": ["type:lib", "scope:adapter"],
  "targets": {
    "build": {},

    "test": {}
  }
}
```
